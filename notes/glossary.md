## まず押さえる GCP 全体地図と IAM 3 原則

個別のサービスや問題に入る前に、Google Cloud 全体の「入れ物」と「権限」の骨格を 2 枚の地図で固定しておきます（図解版は Web アプリの **Week 0：骨格図** を参照）。

### 地図 1：リソースの木構造 vs 木の外のプリンシパル（＋物理配置の別軸）

```text
[管理・権限・課金の木]                          [物理配置（別の軸）]
組織 (Organization)  ※会社に1つ、木の根          マルチリージョン (asia / us)
 └─ フォルダ (Folder) ※部門・環境（本番/開発）      └─ リージョン (例: asia-northeast1 東京)
     └─ プロジェクト (Project) ※課金・API単位         └─ ゾーン (-a / -b / -c)
         ├─ GCS バケット（個別リソース）         ※ 1 プロジェクト内に複数リージョン混在可
         ├─ Cloud Run（個別リソース）
         └─ サービスアカウント（リソース 兼 ID）

--- 木の境界 ---
Google アカウント・グループ（木の外：Cloud Identity で管理される人間の ID）
```

### 地図 2：フォルダ運用とポリシー継承の実例（IAM vs 組織ポリシー）

- **組織**：全社共通の **組織ポリシー（ガードレール）** を強制（例：SA の静的 JSON キー作成禁止）
- **フォルダ：広告事業部**：`広告チーム＝閲覧者`（上位に弱い権限 → 配下の本番・開発の両方へ継承）
  - **フォルダ：本番** → `ads-rag-prod`：`SRE のみ＝編集者`（継承結果＝広告は閲覧＋SRE は編集）
  - **フォルダ：開発** → `ads-rag-dev`：`開発者＝編集者`（継承結果＝広告は閲覧＋開発者は編集）
- **フォルダ：データ基盤部**：別枝のため、広告事業部の権限は届かない（横には継承されない）

### すべての週に効く IAM の 3 原則

1. **パーミッションは直接付けず「ロール」で束ねる**：`storage.objects.get` のような細かい操作を 1 つずつ付与せず、`roles/storage.objectViewer` のようなロール単位で割り当てる。
2. **ポリシーはリソース側に付き、下へ「足し算」で継承される**：親で許可した Allow は子で取り消せない。だから**上位に弱い権限・下位に強い権限**を置く。
3. **サービスアカウント（SA）は「リソース」兼「プリンシパル（ID）」**：プロジェクト配下に属する箱でありつつ、アプリが他リソースを操作するときの主体にもなる（だから SA 自体にも `actAs` 等の IAM ポリシーを付けられる）。

## 共通・基本用語（Web / クラウド基礎）

### IAM（Identity and Access Management）
- **一言**：Google Cloud 内で「**誰が**」「**何に対して**」「**どんな操作をしてよいか**」を管理する仕組み。
- **イメージ**：会社の入館証と各部屋のアクセス権台帳。
- **ポイント**：すべての Google Cloud サービスに横断して効く土台。基本は「プリンシパル（誰）× ロール（何ができる）× リソース（どこで）」の 3 点セットで考える。

### プリンシパル（主体 / Principal）
- **一言**：Google Cloud を操作する「**誰か**」のこと。人間の Google アカウントだけでなく、サービスアカウントや Google グループも含む。
- **イメージ**：入館証を持っている「人」や「ロボット」そのもの。
- **ポイント**：試験やトラブル調査では、まず「今アクセスしようとしているプリンシパルは誰か（人か、CI か、アプリの実行時 ID か）」を特定する。

### ロール（Role）と権限（Permission）
- **一言**：個別の操作許可が「**権限**」（例：`storage.objects.get`）、それらを用途別に束ねたセットが「**ロール**」（例：`roles/storage.objectViewer`）。
- **イメージ**：権限＝「コピー機を使う権利」「金庫を開ける権利」、ロール＝「経理担当」「閲覧専用ゲスト」という役割パック。
- **ポイント**：Google Cloud では権限を 1 つずつ直接付けるのではなく、ロール単位でプリンシパルに付与する。

### 最小権限の原則（Least Privilege）
- **一言**：目的を果たすのに必要な**最小限の権限だけ**を渡し、余計な権限は付けないセキュリティの基本原則。
- **イメージ**：掃除業者に「会議室の鍵」だけ渡し、社長室の金庫の鍵は渡さない。
- **ポイント**：PCA 試験で最頻出の判断軸。読み取りしか不要なアプリに書き込み権限や `Editor` を付ける選択肢は原則不正解になる。

### サービスアカウント（Service Account / SA）
- **一言**：人間ではなく、**アプリや CI などのプログラムが Google Cloud を操作するときに使う専用アカウント**。
- **イメージ**：社員証の「システム・ボット版」。パスワードではなくトークン等で認証する。
- **ポイント**：デフォルトのサービスアカウントは権限が広すぎるため、本番・演習とも**用途別の専用 SA**を作って必要最小限のロールだけを付ける。

### コンテナ（Container）
- **一言**：アプリ本体と、それを動かすのに必要なライブラリや設定を**ひとまとめに梱包した実行単位（箱）**。
- **イメージ**：中身と道具が一式入った引っ越しコンテナ。どの環境（Mac でも Cloud Run でも）でも同じように動かせる。
- **ポイント**：Cloud Run はこのコンテナを渡すだけで自動で公開・スケーリングしてくれる。

### HTTP ステータスコード（200 / 401 / 403）
- **一言**：Web リクエストの結果を伝える 3 桁の番号。`200`＝成功、`401`＝認証エラー（誰かわからない）、`403`＝認可エラー（身元はわかったが権限がない）。
- **イメージ**：`401`＝「社員証を見せてください」、`403`＝「社員証は確認できたが、この部屋には入れません」。
- **ポイント**：Cloud Run の入口で 403 なら Invoker 不足、入口は通過したのに裏で 403 なら実行時 SA のデータ権限不足と切り分ける。

### API（Application Programming Interface）
- **一言**：アプリや CI から Google Cloud の機能（バケットを読む、シークレットを取る等）を**プログラム経由で呼び出すための窓口**。
- **イメージ**：レストランの注文カウンター。ルール通りにリクエストを送ると、裏側で処理して結果を返してくれる。
- **ポイント**：Google Cloud の操作は裏側ではすべて API 呼び出し。API を呼ぶときは認証トークンと IAM 権限の両方が必要。

### CI / CD（継続的インテグレーション / デリバリー）
- **一言**：コードを GitHub などに push したときに、**自動でテスト・ビルド・デプロイを走らせる仕組み**（GitHub Actions、Cloud Build など）。
- **イメージ**：原稿を提出すると自動で校正・印刷・棚への配置までやってくれる全自動ライン。
- **ポイント**：GitHub Actions のような「**外部 CI**」は Google Cloud の外で動くため、キーレス認証には Workload Identity Federation を使う。

### 同期処理 と 非同期処理
- **一言**：**同期**＝リクエストのその場で判定・結果を待つ仕組み。**非同期**＝裏側で後から集計・通知・処理を進める仕組み（時間差＝ラグがある）。
- **イメージ**：同期＝レジでその場で残高チェック、非同期＝月末に届くクレジットカード明細メール。
- **ポイント**：Part 4 の核心。クォータや `max-instances` は**同期**でその場で止まるが、予算アラートは**非同期**のためラグがあり自動停止に使えない。

## Part 1：Cloud Run と 3 つの権限境界

### Cloud Run
- **一言**：コンテナを渡すだけで動かせる**フルマネージドなサーバーレス実行基盤**。アクセスに応じて自動増減し、使わないときは 0 台まで縮小できる。
- **イメージ**：お客さんが来たときだけ店員が増えて、誰もいないときは家賃ゼロになるポップアップ店舗。
- **ポイント**：サーバー構築や OS パッチ管理が不要。PCA では「コンテナを最小運用で動かしたい」ときの第一候補。

### Cloud Storage と バケット / オブジェクト
- **一言**：PDF・画像・テキストなどのファイルを容量無制限で保管できるクラウド倉庫。入れ物が**バケット**、中のファイルが**オブジェクト**。
- **イメージ**：バケット＝倉庫の部屋、オブジェクト＝部屋に置くダンボール箱。
- **ポイント**：読み取り専用なら `roles/storage.objectViewer` を「プロジェクト全体」ではなく**対象バケット単体**に絞って付けるのが最小権限。

### 実行時サービスアカウント（サービス ID / ランタイム ID）
- **一言**：Cloud Run 上で動いている**アプリ自身が、裏側の Storage や Secret Manager へアクセスするときに名乗る ID**。
- **イメージ**：お店の中で倉庫へ荷物を取りに行く「スタッフの名札」。お客さん（呼び出し元）の名札とは別物。
- **ポイント**：「呼び出し元に Storage 権限を付けてもアプリは読めない」という頻出ひっかけの核心。データを読むのは実行時 ID。

### Invoker（`roles/run.invoker`）
- **一言**：非公開の Cloud Run サービスの**入口を呼び出してよい許可**を与えるロール。
- **イメージ**：会員制店舗の「入店許可証」。
- **ポイント**：デプロイ担当者や実行時 ID ではなく、**呼び出し元（クライアント／社内アプリ等）**に対して付与する。

### `actAs`（`iam.serviceAccounts.actAs`）
- **一言**：「**このサービスアカウントをアプリに割り当てて使ってよい**」という許可。代表ロールは `roles/iam.serviceAccountUser`。
- **イメージ**：「このロボットを動かしてよい」という委任許可。
- **ポイント**：デプロイ権限だけで強い SA を勝手に割り当てられる「権限昇格」を防ぐための仕組み。拒否されたら**割り当て先 SA 側の IAM**を見る。

### Control Plane と Data Plane（設定時 vs 実行時）
- **一言**：**Control Plane**＝デプロイや権限設定などの「管理・設定側」、**Data Plane**＝実際のユーザーリクエストやデータ読み書きの「実行側」。
- **イメージ**：Control Plane＝店舗の設計・シフト管理、Data Plane＝実際の接客と商品受け渡し。
- **ポイント**：Cloud Run の障害は「設定時（デプロイ）」「入口（Ingress）」「実行時（Data Plane）」の 3 境界に分けると一発で原因が絞れる。

### 基本ロール（Owner / Editor / Viewer）と事前定義ロール
- **一言**：**基本ロール**はプロジェクト全体に広く効く昔ながらの粗いロール。**事前定義ロール**はサービス・操作ごとに細かく用意された推奨ロール。
- **イメージ**：基本ロール＝全室のマスターキー、事前定義ロール＝「倉庫の閲覧だけできる鍵」。
- **ポイント**：本番や試験で `Editor` などの基本ロールを選ぶのは原則 NG。必要な事前定義ロール（例：`roles/storage.objectViewer`）を選ぶ。

## Part 2：鍵を使わない認証（ADC / WIF / トークン）

### サービスアカウントの JSON キー
- **一言**：サービスアカウントになりすますための**秘密鍵が入った JSON ファイル**。
- **イメージ**：無期限でコピーし放題の「物理の合い鍵」。
- **ポイント**：手動で消すまでずっと有効なため漏えい時の被害が大きく、管理負担も重い。Google Cloud では**発行しない（キーレス運用）**のが鉄則。

### 短命トークン（Short-lived Credentials）
- **一言**：数分〜約 1 時間で**自動的に期限切れになる使い捨ての認証情報**。
- **イメージ**：1 時間だけ有効な自動失効パス。
- **ポイント**：期限前にライブラリが自動で取り直す。仮に漏えいしても影響時間がごく短く、鍵のローテーション運用も不要になる。

### ADC（Application Default Credentials）
- **一言**：コードに鍵の読み込みを書かなくても、Google Cloud のクライアントライブラリが**実行環境に合わせて認証情報を自動探索する仕組み**。
- **イメージ**：職場では社員証、自宅では自宅キーを自動でポケットから取り出してくれる仕組み。
- **ポイント**：Cloud Run 上ではメタデータサーバーから実行時 ID の短命トークンを取得し、ローカル Mac では `gcloud auth application-default login` の認証情報を拾う。

### メタデータサーバー（`metadata.google.internal`）
- **一言**：Cloud Run や Compute Engine の**中からだけアクセスできる Google Cloud 内部の窓口**（IP：`169.254.169.254`）。
- **イメージ**：社内ネットワークからだけつながる「入館証の自動発券機」。
- **ポイント**：アプリが JSON キーを持たずに短命トークンを受け取れる理由。外部 CI（GitHub Actions 等）からは届かない。

### OIDC トークン（OpenID Connect トークン）
- **一言**：GitHub Actions などの外部サービスが、**「今動いているのは間違いなくこのリポジトリのジョブだ」とデジタル署名付きで証明する短命の身分証**。
- **イメージ**：発行元の公印が入った、数分で失効するその場限りの入場証。
- **ポイント**：Workload Identity Federation にこの OIDC トークンを見せることで、JSON キーなしで Google Cloud の短命トークンと交換できる。

### Workload Identity Federation（WIF / Workload Identity 連携）
- **一言**：Google Cloud の**外側**（GitHub Actions・AWS・Azure 等）の身分証（OIDC トークン等）を、**Google Cloud の短命トークンに交換してくれる仕組み**。
- **イメージ**：外部のパスポートを確認して、GCP 専用の 1 時間パスに交換してくれる「両替所」。
- **ポイント**：試験で「外部 CI / AWS / Azure からキーレスで GCP を呼ぶ」と出たら最有力候補。必ず**リポジトリやブランチの属性条件**で許可対象を絞る。

### STS（Security Token Service）
- **一言**：Workload Identity Federation の裏側で、**外部の OIDC トークンを検証して Google Cloud の短命トークンへ交換するサービス**。
- **イメージ**：両替所の窓口でパスポートの真偽をチェックして交換券を渡す担当者。
- **ポイント**：外部 CI 認証のフローでは「外部 IdP（OIDC 発行）→ GCP STS（交換）→ GCP API 呼び出し」の順で動く。

### ID トークン と OAuth アクセストークン
- **一言**：**ID トークン**は「誰が・誰宛て（`aud`）に呼んだか」を示す身分証、**OAuth アクセストークン**は「Google Cloud API を操作する通行証」。
- **イメージ**：ID トークン＝宛名付きの名刺、OAuth アクセストークン＝施設内の利用チケット。
- **ポイント**：非公開 Cloud Run の入口認証には **ID トークン**、Cloud Storage などの Google API 呼び出しには **OAuth アクセストークン**を使う。

### サービスアカウントの借用（Impersonation）
- **一言**：JSON キーをダウンロードせず、許可されたユーザーが**一時的に別サービスアカウントの権限を借りて操作・検証する仕組み**（`--impersonate-service-account`）。
- **イメージ**：管理者の立ち会いのもと、その場だけ作業用の名札を借りて動作確認すること。
- **ポイント**：Mac ローカルで「本番の実行時 SA と同じ権限で動くか」を安全にテストしたいときに使う。

## Part 3：リソース階層と Secret Manager

### リソース階層（組織 → フォルダ → プロジェクト → リソース）
- **一言**：Google Cloud のすべてのリソースを整理する**4 段階の入れ子構造**。
- **イメージ**：会社（組織）→ 事業部・部署（フォルダ）→ チーム案件（プロジェクト）→ 個別のファイルや金庫（バケット／シークレット）。
- **ポイント**：IAM ポリシーはこの階層の上から下へ自動的に引き継がれる。付与する階層を 1 段上げるだけで影響範囲が一気に広がる。

### Allow ポリシーの継承（和集合）
- **一言**：上位階層で付けた Allow（許可）は、**配下の全リソース（将来作られるものも含む）へ「足し算」で継承される**ルール。
- **イメージ**：ビル全体に入れるパスを持つ人は、各部屋の許可リストに名前がなくても入れてしまう。
- **ポイント**：子リソース側の IAM を空にしても上位の許可は消せない。「子に載っていないのに読める」ときはプロジェクト・フォルダ・組織・グループを確認する。

### IAM Deny ポリシー（許可しない）
- **一言**：上位から継承された Allow より**優先して特定の操作を強制ブロック**するルール。
- **イメージ**：全館パスを持っていても「この部屋だけは絶対立入禁止」と止める非常ロック。
- **ポイント**：まず「上位の広すぎる Allow を外す」のが第一選択。広い Allow を維持しつつ例外的に操作を禁止したいガードレール用途で使う。

### Secret Manager
- **一言**：API キーや DB パスワードなどの**秘密情報を暗号化して安全に保管・バージョン管理するサービス**。
- **イメージ**：鍵のかかった専用の貸金庫。誰がいつ開けたかも監査ログに残る。
- **ポイント**：アプリに 1 件だけ読ませたいときは、プロジェクト全体ではなく**対象シークレット単体**に `roles/secretmanager.secretAccessor` を付ける。

## Part 4：予算通知とクォータ（FinOps）

### Cloud Billing と 予算アラート（Budget）
- **一言**：GCP の利用料金を集計する仕組みが **Cloud Billing**。設定した金額のしきい値（50% / 90% / 100% 等）に達したらメールや Pub/Sub で知らせるのが **予算アラート**。
- **イメージ**：利用額を教えてくれる「お知らせアラーム」。**ブレーカー（自動停止装置）ではない**。
- **ポイント**：課金データの集計には数分〜数時間の非同期ラグがあり、予算に達しても利用は止まらない。

### クォータ（Quotas / 割り当て）
- **一言**：API リクエスト数や vCPU 数など、**サービスごとのリソース利用量を同期的に頭打ちにする上限設定**。
- **イメージ**：蛇口に付ける「1 分あたりの最大水量リミッター」。
- **ポイント**：金額（円・ドル）の上限ではなく**利用量**の上限。暴走課金を防ぐために予算アラートとセットで設計する。

### `max-instances`（最大インスタンス数）
- **一言**：Cloud Run がアクセス急増時に自動スケールで増やせる**コンテナ数の上限設定**。
- **イメージ**：混雑時に増やせるレジ台数の上限。
- **ポイント**：リクエスト到達時に同期的に判定されるため、バグやスパイクによる想定外の課金暴走を物理的に頭打ちにできる。

### Pub/Sub
- **一言**：イベントや通知メッセージ（予算超過通知など）を、**送信側と受信側を切り離して非同期に配信するメッセージングサービス**。
- **イメージ**：お知らせを投函すると、登録しているシステムへ自動で配達してくれる郵便局。
- **ポイント**：予算アラートの通知先に Pub/Sub を指定すれば自動処理を起動できるが、集計〜通知〜実行のラグがあるため「100% ピッタリ停止」にはならない。

## 全体像（ロードマップに出てくる主なサービス）

### PCA / PAA（認定資格）
- **一言**：**PCA**＝Professional Cloud Architect（クラウド設計・運用全般の認定）、**PAA**＝Professional Agentic Architect（AI エージェント基盤の設計・運用の認定）。
- **イメージ**：PCA＝建物全体のインフラ設計士、PAA＝その上で動く自律 AI チームの設計士。
- **ポイント**：この学習計画では前半 24 週で PCA の土台を固め、後半半年で PAA へ進む。

### GKE / Compute Engine（GCE）
- **一言**：**GKE**（Google Kubernetes Engine）はコンテナ群を高度に管理する基盤、**Compute Engine** は仮想マシン（VM）を直接借りる基盤。
- **イメージ**：Cloud Run＝おまかせ店舗、GKE＝複数店舗を統括する商業ビル管理、Compute Engine＝土地から自分で建てる自由設計。
- **ポイント**：第 7 週で Cloud Run・GKE・Compute Engine の 3 択を「運用負荷・スケール・特殊要件」で比較する。

### Cloud SQL / Cloud Spanner / Firestore / BigQuery
- **一言**：用途別のデータ保存・分析サービス。**Cloud SQL**＝定番 RDB、**Spanner**＝世界規模で整合性を保つ RDB、**Firestore**＝JSON 風ドキュメント DB、**BigQuery**＝超大規模データ分析倉庫。
- **イメージ**：日常の台帳（SQL）、世界同時更新の銀行元帳（Spanner）、柔軟なメモ帳（Firestore）、過去数年分を集計する分析室（BigQuery）。
- **ポイント**：第 8〜9 週で「トランザクション・一貫性・データ量・分析用途」から選び分ける。

### VPC（Virtual Private Cloud）
- **一言**：Google Cloud 上に作る**自分専用の仮想ネットワーク空間**。サブネット・ルート・ファイアウォールで通信経路と許可を制御する。
- **イメージ**：自社ビル専用の構内 LAN とセキュリティゲート。
- **ポイント**：第 5〜6 週のメインテーマ。公開入口とプライベート通信経路を区別して設計する。

### Terraform（IaC：Infrastructure as Code）
- **一言**：GCP のバケットや IAM 設定を手作業クリックではなく**コード（設定ファイル）で書いて管理・自動反映するツール**。
- **イメージ**：建物を毎回手作業で建てる代わりに、設計図ファイルから同じ環境を何度でも正確に再現する仕組み。
- **ポイント**：第 11 週で `plan`（変更差分の事前確認）と `state`（現在の構成記録）の仕組みを実践する。
